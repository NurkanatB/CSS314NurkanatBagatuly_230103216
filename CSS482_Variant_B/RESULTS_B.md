Verification (all runs gave the same step sum 131,434,424): **PASS**. Each chunk configuration uses its own P=1 baseline.

**Measured:** at P=8 the micro-task run reached S=0.90 (e=1.131) while the coarse run reached S=4.72 (e=0.099). Even at P=1, k=1 took 34.35 s versus 11.90 s for k=10,000 (2.89x), which isolates pure dispatch/pickling cost.

**Why chunking helps.** With `chunksize=1`, `Pool.map` creates 1,000,000 task envelopes. Each is pickled by the master, pushed through a shared pipe, unpickled by a worker, and its result is pickled back. That per-task cost is comparable to or larger than the work (a Collatz walk is only ~100 loop iterations on average), and the master is a single serial dispatcher, so it becomes the bottleneck. With `chunksize=10,000` only 100 envelopes exist; each carries a block of numbers, so the fixed IPC cost is amortized over thousands of items and workers compute with almost no master involvement. Note that Collatz cost is uneven, so a few large chunks can also cause some load imbalance.

## C. Experiment B - IPC Queue Choke-Point (400,000 items)

| P | Runtime (s) | Speedup | Runtime vs T1 | Karp-Flatt |
|---|---|---|---|---|
| 1 | 8.768 | 1.00 | 1.00x | n/a |
| 2 | 30.479 | 0.29 | 3.48x | 5.953 |
| 4 | 30.976 | 0.28 | 3.53x | 4.377 |
| 8 | 30.339 | 0.29 | 3.46x | 3.812 |

Verification (master collected exactly 400,000 items per P, checksums match): **PASS**. Runtime strictly monotonic in P: **False**.

**Measured:** T1=8.77 s, T8=30.34 s (T8/T1 = 3.46x); e(2)=5.95, e(8)=3.81.

**Explanation.** `multiprocessing.Queue.put` appends to a buffer; a background feeder thread in each worker pickles the item and writes it to a shared OS pipe guarded by a cross-process write lock. With P producers all writing single tiny items, they fight over that lock (each acquisition is a syscall and potentially a context switch), while the master's single `get()` loop - which also takes a read lock, unpickles one item at a time - is a strictly serial consumer. Total useful work per item is trivial (`i % 7`), so the run time is almost entirely synchronization: adding processes adds lock contention, scheduler switches and cache-line ping-pong without adding consumption capacity. That is negative scaling: here T8 > T1, i.e. adding producers made the run slower.

**Expected vs observed.** The handout quotes illustrative values (e.g. T1~1.2 s, T8~7.6 s, e(8)~6.28). Absolute times depend on CPU, Windows scheduler and Python version, so they will differ. What should carry over is the *shape*: T increasing with P and e(p) rising. Measured runtime jumped from 8.77 s (P=1) to about 30-31 s for P=2, 4 and 8, so T8 > T1 and negative scaling is confirmed. The increase was a one-time step followed by a plateau, not a monotonic rise, and e(p) decreased (5.95 -> 4.38 -> 3.81) because Tp stayed roughly constant while p grew. This differs from the handout's expected shape. A plausible explanation (not isolated experimentally) is that once more than one producer shares the pipe, throughput is limited by a single serialized channel (write lock plus the master's single get() loop), so extra workers add contention but no capacity.

## D. Experiment C - Local Buffer Chunking (10,000,000 items, batch 10,000)

| P | Runtime (s) | Speedup | Efficiency (%) | Karp-Flatt |
|---|---|---|---|---|
| 1 | 1.033 | 1.00 | 100.0 | n/a |
| 2 | 0.579 | 1.78 | 89.2 | 0.1208 |
| 4 | 0.405 | 2.55 | 63.8 | 0.1894 |
| 8 | 0.380 | 2.72 | 34.0 | 0.2775 |

Verification (totals equal closed-form expected sums): **PASS**.

**Throughput comparison.** Exp C processed 25x more items than Exp B. B's P=8 run handled 13,185 items/s; C's P=8 run handled 26,313,774 items/s (1996x higher). At P=1: B 45,622 items/s vs C 9,679,092 items/s.

**Why aggregation helps.** Each worker now does its per-item work in a private Python list (no locks, no pipe). It crosses the IPC boundary once per 10,000 items, so the queue sees ~1/10,000th of the messages (about 1,000 puts in total instead of 10,000,000 if unbuffered). Synchronization cost is amortized, the master's serial work becomes negligible, and the remaining runtime is genuinely parallel computation. Process start-up (spawn on Windows re-imports the module) is the main fixed cost left.

## F. Technical Discussion

1. **Small tasks and scheduling overhead.** Every dispatched task costs a fixed amount of pickling, pipe I/O, wake-up and result return, paid by the master and a worker. If the work per task is comparable to that cost, the serial master saturates and workers idle (Experiment A, k=1).
2. **Shared queues as bottlenecks.** A `Queue` is one pipe with locks and one reader. Producers serialize on the write lock and the consumer serializes on reads, so throughput is capped by a single channel and more producers only add contention (Experiment B).
3. **Batching.** Aggregating locally replaces N messages by N/batch messages, so fixed per-message cost shrinks by the batch factor (Experiment C and Experiment A with k=10,000).
4. **Karp-Flatt.** e(p) is the experimentally implied serial fraction. A flat e(p) across p=2,4,8 indicates a constant serial fraction (Amdahl-like); an e(p) that rises with p indicates overhead growing with the process count: lock waits, dispatch, IPC, oversubscription. Caveat: on a machine with fewer than 8 logical CPUs, oversubscription inflates e(8) in every experiment.
5. **More workers is not always better.** Overhead can scale with p (contention, context switches, process start-up) and physical cores are finite; beyond the point where overhead growth exceeds the added compute, runtime rises.
6. **Best optimization per experiment.** A: increase `chunksize` (or use `imap_unordered` with a sensible chunk). B: stop sending per-item messages - batch or aggregate in the worker. C: already near-optimal; remaining gains come from reducing process start-up or using a faster per-item loop, and from matching P to physical cores.

## G. Conclusion

**Measured:** see the tables above for the exact figures. Experiment A shows the cost of per-task dispatch and its removal by chunking; Experiment B isolates IPC cost by making work trivial and messages maximal; Experiment C removes that cost with local aggregation. On this machine: A-micro S8=0.90, A-coarse S8=4.72, B S8=0.29, C S8=2.72.

**Theoretical expectation (not a measurement):** well-amortized CPU-bound work should scale close to the number of *physical* cores, with a small, flat e(p); communication-bound work should show e(p) that grows with p. Any difference between those expectations and the table is attributable to the hardware, the OS scheduler, SMT (logical vs physical cores) and the Python/spawn startup cost, and is reported here as observed rather than adjusted.

The handout's targets for Experiment C (S8 > 5, e(8) <= 0.05) were not met on this 6-core/12-thread laptop (measured S8 = 2.72, e(8) = 0.278). Likely contributors are Windows process start-up included in the timer and P=8 sharing physical cores; these were not measured separately.
