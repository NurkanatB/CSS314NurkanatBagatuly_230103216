## Mathematical summary
* Gustafson: S_G(P) = P − α(P−1) = 1 + (1−α)(P−1); E_G = 1 − α + α/P → 1 − α.
* Amdahl: S_A(P) = 1/[s + (1−s)/P] → 1/s; E_A = 1/[sP + 1 − s] → 0.
* α: serial fraction on the parallel machine (scaled workload); s: serial fraction of the fixed-size, one-processor run; P: processors/workers.
* Maximum tolerable serial fraction: α_max = (P − S_req)/(P − 1).
* With communication: S_mod = S_G/(1 + γ(P)). Sun–Ni: S* = [α + (1−α)G]/[α + (1−α)G/P].

## Amdahl vs. Gustafson
| | Amdahl | Gustafson |
|---|---|---|
| Invariant | problem size | execution time |
| Speedup limit | 1/s | unbounded |
| Example α = s = 0.08, P = 128 | 11.47 | 117.84 |
| Example α = s = 0.04, P = 16384 | 24.96 | 15728.68 |

```bash

python -m benchmarks.weak_scale_bench.runner --repetitions 5            # Task 22/23: writes benchmarks/results.csv
```

(on a machine with fewer than 5 distinct counts up to the CPU count, pass explicit counts, aware of oversubscription).

## Results interpretation
* Theory tables (Tasks 06–10, 16–17) are exact calculations; plots `*_theory.*` and `efficiency_comparison.*` are model curves.
* The committed `benchmarks/results.csv` was produced in a **1-CPU sandbox**: it shows oversubscription (S ≈ 0.7–1, fitted α ≈ 1.03 outside [0,1]); it validates the toolchain but does **not** measure a real serial fraction. Re-run on your machine and re-generate the plots and `analysis/task24_hardware_audit.md` hardware section.

## Conclusions for parallel software engineers
See `analysis/conclusions.md`: measure α on the parallel machine at several P, design for weak scaling when the problem can grow, eliminate O(P) serial steps, use tree collectives, avoid global synchronisation, and report strong and weak scaling separately.
